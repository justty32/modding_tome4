# spec — 盧恩術士（Runewright）

> 狀態：**設計定案，API 綁定待複驗**。標「⚠️API」的地方必須回 `vendor/t-engine4/` 原始碼確認後才動工。

## 一句話

一個把 ToME 既有的**銘文（inscription）系統**從「消耗品插槽」變成「職業核心資源」的奧術職業：他不是用符文，他**寫**符文。

## 為什麼是這個設計

ToME 的銘文系統（符文 / 輸能）是全職業共用的道具欄位，多數職業只是塞三個治療符文就不管了。這給了一個沒人佔的設計空間：**讓一個職業擁有它**。

好處有三：
1. 機制上獨特——沒有既有職業以銘文為主軸。
2. 實作上省力——引擎已有 inscription 的資料結構與冷卻邏輯，我們是擴充而非重造。
3. **天然需要自訂 UI**——玩家要看到自己「刻了什麼、充能多少、下一個共鳴是什麼」，內建的技能列表表達不了。這正是你要的技能面板的存在理由。

## 核心機制：銘刻與共鳴

### 資源：符文充能（Rune Charge）⚠️API

- 上限隨等級與 `spell/runic-mastery` 成長。
- **獲得**：每次觸發任一銘文（符文／輸能）+1；施放 `spell/runecraft` 系技能 +1。
- **消耗**：高階技能與「共鳴」。
- 不自然回復——不用銘文就沒充能。這強迫玩家真的去玩銘文系統。

⚠️API：自訂資源要用 `ActorResource:defineResource`，簽名與呼叫時機待確認。若成本過高，退路是用既有 `mana` + 一個 `self.rune_charge` 欄位（不進資源條，只進自訂 UI 面板）。

### 共鳴（Resonance）

當玩家身上**同時存在**特定銘文組合時，被動獲得額外效果。**已實作並實機驗證**：

| 組合 | 共鳴 | 效果 |
|---|---|---|
| 法力風暴符文 + 回覆紋身 | 泉湧共鳴 | 法力回復 +0.5，法術強度 +5 |
| 護盾符文 + 治療／回覆紋身 | 壁壘共鳴 | 護盾吸收量 +25%，受到治療 +15% |
| 傳送符文 + 迅捷紋身 | 迅影共鳴 | 移動速度 +20%，暈眩與定身抗性 +30% |
| 身上 3 個以上符文 | 三相共鳴 | 造成傷害 +10%，銘文屬性加成 +15% |

**泉湧共鳴刻意對準原版預設起始銘文**（法力風暴 + 回覆 + 狂暴），所以玩家第一回合就看得到共鳴運作，
而且完全不必更動起始配裝、沒有平衡疑慮。這比原本「送兩個特製銘文」的做法乾淨——
何況那做法根本不生效：銘文欄位只有 3 個，多的會被 `setInscription` 靜默丟棄。

共鳴是**湧現式**的：玩家自己搭配銘文組合去發現。這是整個職業的樂趣來源，也是 UI 面板必須存在的原因——沒有面板，玩家根本看不到自己觸發了什麼。

實作要點：
- 判定與效果都是 `data/lib/resonance.lua` 裡的**純資料**（`matches` + `effects`），
  套用由 `superload` 的 `runewrightApplyResonanceEffects()` 泛用地 `addTemporaryValue`。
- 比對用銘文天賦的 `short_name`，**不可用 `t.name`**（那是已翻譯的）。
- 由「共鳴之心」的 `callbackOnActBase` 每回合重算；集合沒變就早退，不重建 temporary value。
- ᛗ Mannaz 的加成隨啟動中的共鳴數量浮動，同樣在 sync 裡重算。

## 技能樹

分兩層：**核心三棵**是資源引擎，**古弗薩克文三族**是符文內容本身。

### 核心（資源引擎）

| 技能樹 | 類型 | 起手 | 主題 |
|---|---|---|---|
| `spell/runecraft`（盧恩銘刻） | class | ✅ 解鎖 | 產生／消耗符文充能 |
| `spell/runic-mastery`（盧恩精通） | class, 被動 | ✅ 解鎖 | 充能上限、銘文效力、開啟共鳴 |
| `spell/inscription-lore`（銘文學識） | **generic** | ✅ 解鎖 | 額外銘文欄位 |

### 古弗薩克文三族（Elder Futhark ættir）

**這不是硬套**：古弗薩克文本來就是 24 個符文分成三個 ættir，各 8 個。
每族取 4 個符文成一棵技能樹，族的傳統主題直接對應機制。

| 技能樹 | 起手 | 符文 | 主題 |
|---|---|---|---|
| `spell/futhark-freyr`（弗雷之族） | ✅ 解鎖 | ᚠ Fehu 流轉／ᚦ Thurisaz 巨人之刺／ᚲ Kenaz 火炬／ᚹ Wunjo 圓滿 | 顯化：資源轉換與烈焰 |
| `spell/futhark-heimdall`（海姆達爾之族） | 🔒 類別點解鎖 | ᚺ Hagalaz 冰雹／ᛁ Isa 冰封／ᛉ Algiz 庇護／ᛊ Sowilo 勝利之光 | 試煉：阻絕與守護 |
| `spell/futhark-tyr`（提爾之族） | 🔒 類別點解鎖 | ᛏ Tiwaz 勝利之矛／ᛖ Ehwaz 駿馬／ᛗ Mannaz 人之符／ᛟ Othala 祖產 | 傳承：把充能與共鳴兌現 |

第一族以 Fehu 起首、第三族以 Othala 收尾——從「財富的流動」到「世代的傳承」，
這是符文序列本身的敘事，剛好也是這個職業從累積到爆發的節奏。

### 三族如何咬合核心機制

- 多數符文技能使用後 **+1 符文充能**（餵給核心）。
- ᚠ Fehu 把充能換成法力；ᛏ Tiwaz 消耗全部充能換取傷害倍率。
- ᛗ Mannaz 的加成**隨啟動中的共鳴數量浮動**——它是共鳴機制的第一個實際數值出口。
  因為是動態的，不能寫在天賦的 `passives`（只在學習時算一次），
  而由 `superload` 的 `runewrightSyncResonances()` 在共鳴變動時重算。
- ᛟ Othala 是終極技：同時消耗充能與讀取共鳴數量。

### 已解決：職責重疊

原本 `spell/runecraft` 第 4 位有「護印」（`RW_WARD_SIGIL`，全抗性持續技），
與海姆達爾之族的 ᛉ Algiz 庇護重疊。**2026-07-10 已移除護印**（使用者定調）。

`spell/runecraft` 因此只有 3 個技能，這是刻意的：它是**資源引擎**，
只負責產生與消耗符文充能；防護的職責完全交給 ᛉ Algiz。
一棵樹只做一件事，比湊滿 4 個技能重要。

## 自訂 UI：符文盤（Rune Board）

> **本輪不實作**，但所有資料結構要為它預留。

- 一個可開關的面板，顯示：目前銘文欄位（含冷卻圈）、符文充能條、已啟動的共鳴、以及「若再刻上 X 會觸發 Y」的預測提示。
- 進入點：技能列的一個按鈕 + 快捷鍵。
- ⚠️API：ToME 的 UI 用 `engine.ui.Dialog` 家族；面板要能被 `game:registerDialog` 呼出。實作前先讀 `modules/tome/dialogs/` 的既有面板（例如 `CharacterSheet.lua`）當範本。

**為 UI 預留的約束**：共鳴的判定邏輯必須是一個**純函數** `resonances(inscription_list) -> {resonance...}`，不可以寫在技能的 `on_learn` 裡。因為 UI 面板要對「假設玩家再刻上 X」的假想清單求值來做預測提示。這條約束現在不遵守，之後做 UI 就得重寫。

## Done when（本輪，不含 UI）

1. 選角畫面能選到「盧恩術士」，種族相容性正常。
2. 五個技能樹存在，起手技能可加點。
3. 至少 3 個技能可實際施放且有效果。
4. 符文充能會隨銘文觸發而增減。
5. 至少 1 個共鳴能被觸發並在 log 顯示。
6. `tools/lint.sh` 與 `tools/verify.sh` 皆退出碼 0。

**不包含**：UI 面板、平衡調校、i18n 翻譯、Steam Workshop 上架。
